Built from your answers above:
- Loop solver. Start point mode: the largest-area loop through each start
  point that is no longer than its max length (roads are loaded within half
  that length of the start). Area mode: the roundest loop (highest
  isoperimetric quotient) that encloses at least n% of the shape. Neither
  mode runs the same street twice. One loop per start point, best loop only.
- Rectangle shape (2 opposite corners), next to circle and ellipse.
- mi/km toggle (top right of the panel), default mi, remembered.
- Drag the green flag along a finished loop to choose where to start, and
  a Reverse button. The elevation profile, the arrows and the KML export all
  follow the chosen start and direction.
- Elevation profile with hover (shows the point on the map), total climb.
- Estimated time from a run pace or bike speed.
- KML export (Google Earth / My Maps): the path, a shaded territory polygon
  and the start point.
- Saved loops (this browser only), with their elevation data.
- All road and path types are loaded (footways, paths, cycleways, service
  roads, tracks, steps added).
- Git repository set up with two commits. Nothing pushed anywhere.

Same format as before: answer below each question. "ok" accepts the current
assumption.

--- E. HOW LOOPS ARE SCORED ------------------------------------------------

23. Start point mode maximizes enclosed AREA within the length limit. The
    alternative is maximizing roundness (isoperimetric quotient), as area
    mode does, which would favor shorter, rounder loops over bigger ones.
    Current assumption: maximize area.
    Answer: ok

24. Area mode: when two loops are about equally round and both meet the
    coverage target, should the shorter one win (less running), or doesn't
    it matter?
    Current assumption: roundness only.
    Answer: if the iso-quotient is equal, the one with the greater total area is the better one

25. Area mode: may the loop go outside the drawn shape? Right now roads up
    to 30% beyond the shape are allowed, and area outside the shape neither
    helps nor hurts. Should outside area be penalized, or should the loop
    stay strictly inside?
    Current assumption: up to 30% outside is fine.
    Answer: change to 20% outside

26. Default coverage target for area mode?
    Current assumption: 90%.
    Answer: default 90% good, but configurable (make it easy to understand for the user)

27. How does the INTVL app count territory when a loop crosses or touches
    itself (a figure 8, or two parts meeting at one intersection)? The
    solver currently avoids that entirely. If you know how INTVL computes
    the area (GPS track polygon, a grid of cells, something else), tell me
    and I'll match it exactly.
    Answer: i believe it is just GPS track polygon, but I am not sure the full implications of that. to be honest just keep it how it is.

28. Start points: a loop can only begin at a road intersection, so it
    starts at the point on the loop closest to your pin. A warning appears
    if that's more than about 500 ft away. OK?
    Answer: ok, just let user know that it will start on an intersection

29. If no loop meets the requirements (e.g. the coverage target is too high
    for the roads available), the app shows the best loop it found with a
    warning. Would you rather get no loop at all in that case?
    Current assumption: show it with a warning.
    Answer: ok

--- G. VERY LARGE AREAS (e.g. a loop around Kansas) ------------------------

31. Downloading every road and footpath in a state isn't feasible in a
    browser: Overpass would refuse it, and the graph would have tens of
    millions of points. My proposed plan:
      (1) For big searches, first download only major roads (e.g. primary
          through tertiary) and find a coarse loop on those.
      (2) Then download all roads in a narrow corridor along that coarse
          loop, in chunks, and refine each stretch locally.
    Is that the "chunking" you had in mind? Above what size should it switch
    to this mode (say, loops longer than 30 mi)?
    Answer: ok, use testing to figure out the max distance feasible without chunking, rest will work as you described.

32. For huge loops, is it OK if the coarse stage only uses major roads, so a
    loop around Kansas would mostly follow highways and county roads?
    Answer: yes, however there should be local optimization happening after the coarse one is made, whether thats universal, or just on spots that are calculated to be inefficient.

33. Should very long searches be allowed to run for minutes (with a
    progress bar and the best loop so far drawn live)? The search time
    options are now 3 s, 8 s and 25 s per loop.
    Answer: yes, progress bar, and dynamically update. The user would then be able to export a loop even if its not done searching all the optimizations. it would just give them a slightly outdated file but thats fine for UX
